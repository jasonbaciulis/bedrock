Commit the working changes on a new release branch, create a pull request to main, and create a new release.

## Branch & commit the working changes

1. Run `git status` and `git diff` to understand all uncommitted (staged and unstaged) changes.
2. Create and switch to a new release branch off main: `git switch -c release/<short-descriptive-slug>` (kebab-case, derived from the overall theme of the changes).
3. Group the changes into logical commits — one commit per coherent unit of work, based on which files changed and what was changed together (e.g. a feature, a bugfix, a refactor, a config change should each be their own commit). Stage each group explicitly with `git add <paths>` rather than `git add .`.
4. Write each commit message following the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) spec:
   - Format: `<type>[optional scope]: <description>` — e.g. `feat(stepper): add numeric inputmode to fieldtype`.
   - Common types: `feat`, `fix`, `refactor`, `chore`, `docs`, `style`, `test`, `perf`, `build`, `ci`.
   - Keep it brief: a single sentence, lowercase, no trailing period — a clean one-liner in the GitHub UI.
   - Use `!` after the type/scope (e.g. `feat!:`) for breaking changes.
   - Do not add a body or footer unless a change is genuinely breaking or needs context.
   - Do not mention it's generated by Claude.

## Create the pull request

5. Run `git log main..HEAD --oneline` to see the commits on this branch.
6. Run `git diff main...HEAD --stat` to see changed files.
7. Push the current branch: `git push -u origin HEAD`
8. Create a PR to main using `gh pr create --base main`. Write a concise title (under 70 characters) and a short description summarizing the changes. Use this format for the body:

```
## What's new
<bullet points>

## What's fixed
<bullet points>
```

Don't include anything else. Don't mention it's generated by Claude.

9. Return the PR URL.

## Merge the pull request

10. Merge the PR into main: `gh pr merge --merge` (wait for it to complete). This ensures the new commits are on `main` before the release is tagged.
11. Switch back to main and pull the merged changes: `git switch main && git pull`.
12. Delete the merged release branch locally and on the remote: `git branch -d release/<short-descriptive-slug> && git push origin --delete release/<short-descriptive-slug>`.

## Create the release

13. Determine the current release version by running `gh release list --limit 1` (or `git tag --sort=-v:refname | head -1`). The latest tag looks like `vX.Y.Z`.
14. Ask me whether this should be a **major**, **minor**, or **patch** release, then bump the version accordingly:
    - **major**: bump X, reset Y and Z to 0 (e.g. `2.0.0` → `3.0.0`)
    - **minor**: bump Y, reset Z to 0 (e.g. `2.0.0` → `2.1.0`)
    - **patch**: bump Z (e.g. `2.0.0` → `2.0.1`)
15. Create the release with `gh release create vX.Y.Z --target main --title "vX.Y.Z"`, using the new version. Use the same body format as the PR:

```
## What's new
<bullet points>

## What's fixed
<bullet points>
```

16. Return the release URL.
